# Luma Portal

Use the portal to edit the setup for one Luma profile. Home, Add-ons, Tracking, Tags and Preferences are separate areas. Desktop keeps the profile, section navigation and save action in view. On narrow screens only the draft save bar stays fixed. Switching profiles with an unsaved draft offers Save and switch, Discard and switch, or Keep editing. Keyboard focus uses one inset outline. Selection is shown by the active tab fill, and actions in the same dialog use matching button sizes. The browser writes to the selected Sync server; Luma devices read those changes on their next sync.

The portal at the root is for users. Admin is a separate, unlinked route for the operator, protected by the host's Authelia policy. Admin uses the same Luma theme and separates Users, Invitations and Registration. Invite-only and closed servers retain those rules for app and web registration.

Passkey sessions last an hour. The portal warns you five minutes before the session ends. Changes to the setup are backed up automatically in this browser as an encrypted draft. Once the portal says the draft is secured, you can close or refresh the tab and sign in with the same account in the same browser to pick up where you left off. If browser storage is unavailable, keep the tab open until you can save. Signing out offers to keep the secured draft on this browser or discard it. **Save to Luma Sync** sends the draft to your devices. When a device changed the same setting in the meantime, the portal keeps your draft visible for review and asks you to reload before editing again. Catalog pickers leave out routes that require an input such as a search term.

Use the native sync contract for each field. This includes the field's owner, validation, merge, reset behavior and the first native version that reads it. The browser never edits native platform preference blobs. Build the editor from known portable settings; keep opaque records intact. Provider tokens, API keys, Jellyfin credentials, local PINs and device-specific settings remain outside the browser contract. Managed Trakt, Simkl and MDBList connections can be authorized from Tracking when the server advertises `widgetConnections: 1` and enables the provider. The copy workflow stays in Luma. Choosing a tracking source does not connect the account. Saving a portal draft does not rewrite connection references, native private Library pins or the local Library record. Only the explicit account action writes its own connection reference. The public custom row uses the native LibraryPinnedShelf format and the discovered manifest route.

**Profiles** requires a saved setup. A new profile gets an unused slot (up to six), an independent add-on list, and no copy of Home, tracking, configured links, credentials or watch activity. An inheriting template uses the public list shown on its Add-ons page. The copy preserves order and enabled state. The portal never reuses a deleted slot, because another device may still have pending cleanup of it; reuse is left to Luma.

**Delete profile** (Profiles, Edit current profile) is offered for secondary profiles only and never for the last profile. It writes what a native client writes: the slot's `exists` register becomes false with the next list-wide stamp, and each profile domain that holds a value (settings, common settings, Mac settings, Home content, Home widgets, collections, add-ons, local library) is cleared by a value-less record with the next snapshot counter, all in one publication. Other devices remove the profile on their next sync; older encrypted snapshots and server backups are not erased. Managed Trakt, Simkl and MDBList grants of the profile are revoked after the publication, and a failure is reported so they can be revoked in the provider. The browser cannot undo a deletion. Save or discard setup changes first. Editing an existing profile preserves unrelated field revisions, local-avatar references and PIN metadata. Creating a profile and copying add-ons use one encrypted publication. If the sync cursor moved, reload and review the latest roster before retrying. A shared add-on toggle keeps the profile's own list available if sharing is turned off later.

Home uses the saved placement and instance IDs. An explicit widget suppresses its matching base route even when the widget is hidden; intentional copies and different media types remain separate. The editor and visible Home export use the same placement order. Unplaced folder rows and hidden items are accessible with Show hidden. Moving between Home and a folder is offered only when the destination can represent the settings. Catalog sections own references to the folder's sources; deleting a section retains its catalogs.

Folder controls sit below the cover. Use Reorder to show drag handles, or use Move up and Move down in an item's menu. Home search starts at the current location and shows the path for each result. Home tools has separate views for templates, Home files and animated covers.

The item preview uses the exact manifest identity, media type and catalog ID. Public previews are fetched on selection through the isolated catalog reader. Only a small title/poster projection is returned, and poster URLs must use approved public artwork hosts. Declared genre options can be previewed; personalized or unsupported filters are applied only on the device. Folder covers on approved hosts load when visible. Other supported external covers and animation require a click.

For the local UME acceptance, set `LUMA_TEST_UME=1` when running `test/scripts/sync-editor-smoke.mjs` with the built package and local HTTPS harness. It reads the Lists, Collections, Actors and Directors Luma exports from their `build/evidence/ume-v4-*` directories into a disposable profile; the production UME profile is untouched. The test checks the Home boundary, the original cover images, real Cinemeta posters, move and undo, encrypted native-format readback and Home export.

A change is ready to release when its existing-account and new-account flows pass through local HTTPS, its fields round-trip with the native format and the app reads them on iPhone, Apple TV and Mac. Check mobile width, keyboard navigation, unavailable media, concurrent saves, resets, logout and the protected Admin boundary before changing the live server.

### Per device

Screen size, input and performance differ between devices, so 20 fields (card size, true black, blurs, skip step, banner backdrop, rotation and item count, row orientation, preload, stream badge placement and size, trailer previews, sound and volume) are edited under **Per device**, in tabs for iPhone & iPad (`ios`), Apple TV (`tvos`) and Mac (`macos`). Their register is `<id>@<type>`; each type has its own value. Defaults are the same on every platform (for example skip step 10 s, 5 banner items, no automatic rotation). A device type reads its own register, then the plain `<id>` register older apps wrote, then its default; a reset writes a value-less marker on `<id>@<type>` and wins over the plain register. The portal never writes the plain `<id>` of these fields. Everything else applies to all devices of the profile. `src/lib/luma-sync/swift-contract.test.ts` checks the ids and per-type defaults against `SharedPreferences.swift` (`LUMA_SWIFT_CATALOG`).

The Per device area and its controls are also available in German when the browser uses German. The rest of the portal uses English.

The per-device fields, `home.heroEnabled`, `home.posterTitles/Years` and `playback.streamSort` need a Luma build that reads them; the portal says so next to each. Unchanged fields are never written, so the apps keep their own defaults.

## Devices

The Devices area lists the account's active devices with their added date, and recently removed ones in a collapsed list. Browser sessions are labelled This browser or Web and have no remove action. Remove device asks for confirmation: the device stops syncing, its local data stays on it, and it can be connected again from Luma. The server must advertise `widgetDevices: 1`; otherwise the area explains that device management is unavailable. Device changes are immediate and independent of the setup draft.

## Sync watch activity

Tracking has a Sync watch activity switch per profile. Turning it on lists the connected accounts it covers and writes the consent record a native app writes (`progress.connectedAccounts` in the profile's common settings): a profile tag from the slot's existence stamp, one window per account with its connection reference, the time of consent and the profile library's highest logical clock, at one revision above every setting of the profile; it also chooses Luma as the progress and watchlist source, as the apps do. Turning it off writes the value-less register. The write is immediate and 409-aware, outside the setup draft. The exchange with the providers runs on the user's Luma devices at their next sync; an account connected or replaced after consent waits for confirmation in Luma. The library clock is read from the synced library document and is 0 when no device has opted into the library yet.

## API keys

Preferences starts with an API keys group for the profile's personal TMDB and MDBList keys, shown only when the server advertises `widgetProtectedKeys: 1`. Each provider has a status (Set, Not set, Cannot be read on this server), a masked value with Show and Hide, a password-type input, Save or Replace, and Remove. Keys are sealed in the browser under the space's native secret root and published at once as that provider's register in the profile's common settings, like account connections; they never join the setup draft and need no unsaved-changes state. Apps receive them on their next sync.

The browser opens the root from the copy the server keeps (`GET /v1/native-secret-root`) with a key derived from the content root, verifies it against the commitment, and holds it in memory while the panel is shown. A web-only account creates the root on the first save (`PUT`; the first commitment wins). If a root is committed but its copy cannot be opened, the panel asks you to open Luma on a device that has your keys, sync once and reload, and offers no editing. Registers the browser cannot open are kept as they are. A removal is a sealed empty value with the next odd revision, so it wins over a concurrent edit.

## Sync for configured add-ons

When Luma Sync is already on, a compatible app publishes the profile's installed configured HTTPS manifests automatically. The manager can add an installation, replace its manifest link, rename its label, enable, reorder or remove it. Changes to provider settings such as filters or debrid accounts stay on the provider's own configuration page. An inheriting profile reads the primary profile's list; edit the list in the profile that owns it. Profile selection scopes the UI and edits; it is not a separate encryption boundary within the sync account.

The public `addons` record is unchanged. `commonSettings.v1` carries `addons.configured.v1.<SHA256 of the manifest URL>` registers so older apps retain them as opaque fields. Each AES-GCM value contains the address, name, enabled state and order. A key derived from the content root and authenticated scope binds the value to the sync space, profile, deletion epoch, installation, revision and writer. The native-only metadata key root stays separate. Removing or replacing a link writes a tombstone. A failed manifest check leaves the saved installation intact. Configured catalog selections use the manifest ID, media type and catalog ID, never the private link. The picker omits conflicting IDs when more than one loaded installation declares the same ID.

The browser reads personal manifests in a sandboxed frame while the main portal keeps its restricted network policy. The frame receives the individual address and performs an HTTPS fetch without cookies, auth headers, referrer, persistent cache or automatic redirects. It returns validated manifest identity, name and catalog routes. Personal addresses are absent from the public catalog reader and API calls. If a provider blocks browser reads or requires a redirect, the installation remains editable and the user can import a manifest JSON file for the catalog picker. Verify real configured links in Safari and Chrome and the first sync on an upgraded Apple device before releasing.

Use `NEXT_PUBLIC_LUMA_CONFIGURED_ADDONS=off ./scripts/build-sync-editor.sh` to ship unrelated portal changes before that verification. This build omits the configured add-on editor and manifest reader and leaves the encrypted records untouched.

## Connected tracking accounts

In Tracking, each service shows its provider-confirmed username, connection status and Connect, Switch account or Disconnect action. After signing in to the editor with a Luma passkey, approve Trakt in its own tab. Simkl and MDBList open their approval page with a prefilled code; show the code manually only if needed. The next app sync uses the connection for the same profile on the same server. Provider tokens stay on the server; existing direct app sign-ins stay on the device. The server must advertise `widgetConnections: 1` and enable the selected connector; otherwise the account card explains the missing support.

Save or discard pending setup edits before changing an account. Account actions save immediately to the active profile using the existing encrypted `integrations.<provider>Connection` register. Switching keeps the old account until authorization and publication succeed. Cancelling a pending code removes that attempt, including a late grant. A failed save can be retried without authorizing again; a lost successful reply is recognized from the current register. Concurrent changes to that profile’s connection are never overwritten. Disconnect first revokes the server grant, then publishes the native `disconnected` marker; if publication fails, Retry save finishes it.

Browser sessions have only start, poll, cancel, status and disconnect access. Private provider request relays, account administration remains unavailable. Changing the progress/watchlist source alone does not enable two-way tracking.
